Hajj Crowd Management System 03 / 15
An Engineering Question

If we cannot change WHEN pilgrims must move, we must master HOW.

Where to build? Infrastructure design — which roads are essential to connect all five sites?
Which path? Traffic routing — the safest route given current congestion on each road?
When to depart? Schedule optimization — order groups to minimize total weighted waiting time?

Three questions. Three classical algorithm families. One coherent system.

Hajj Crowd Management System 04 / 15
Modeling the Sacred Sites

Five holy sites become five nodes. Ten roads become ten weighted edges. Each edge carries two values: the physical distance in kilometers, and a congestion-aware weight.

By casting this as a graph, we transform a logistics problem into a mathematical structure with centuries of established theory behind it.

Every algorithm in this project operates directly on this graph. It is the single shared foundation.

From sacred geography to mathematical structure.

Hajj Crowd Management System 06 / 15
Kruskal's MST — Building the Foundation
The Question

Which roads must we build so that every site remains reachable, at minimum total cost?

The Answer

A Minimum Spanning Tree connects every node using exactly N−1 edges, with no redundancy and no cycles. It is the cheapest possible connected network.

Why Kruskal?

Kruskal's provides clear visual reasoning: always select the cheapest available road that does not form a cycle. This maps intuitively to infrastructure planning — build only what is necessary.

Result: 4 essential roads, total length 21.5 km.

Hajj Crowd Management System 07 / 15
Dijkstra's — Routing Under Pressure
The Question

When pilgrims travel between sites, which path carries the least real risk?

The Insight

The shortest road is not always the safest. A 1-km tunnel at 95% capacity is more dangerous than a 3-km open route. Edge weights must encode congestion, not just distance.

The Formula
weight = distance × (1 + load%)

Dijkstra's algorithm then guarantees the globally optimal path — a priority queue always expands the cheapest frontier first, visiting each node exactly once.

Mina to Jamarat: 1.5 km, congestion weight 2.85.

Hajj Crowd Management System 08 / 15
Ten Groups. One Bottleneck. Lives at Stake.

On the day of departure from Mina, ten major pilgrim groups must cross the same critical bottleneck road — one at a time. Each group differs in size, urgency, and the time it requires.

The order matters profoundly. Process the wrong group first and elderly or medically vulnerable pilgrims wait dangerously long. Optimize by urgency alone and the total waiting cost may still be far from minimal.

Hajj Crowd Management System 09 / 15
Three Ways to Decide the Order
Baseline
FCFS
First Come, First Served The naive baseline. Simple. Fair-feeling. Groups are processed in arrival order with no consideration of urgency or cost.
No optimization reasoning applied.
Heuristic
Greedy
Highest urgency first Fast and intuitive. Ensures critical groups are processed early. Achieves a large improvement over FCFS in O(n log n) time.
Clever — but not always the correct answer.
Optimal
Dynamic Programming
Bitmask DP over all subsets Evaluates all 2n possible orderings to find the provably minimum total weighted waiting time.
Provably optimal. Always.

Being fast and being optimal are not the same thing.
